# Serverpod admin app

`examples/serverpod` is the reference workspace: three packages from
`serverpod create` (`bookshop_server`, `bookshop_client`, `bookshop_flutter`)
and two Beak packages under `bookshop_admin` (`generated` and `definitions`).

```text
examples/serverpod/
├── bookshop_server/                 # .spy.yaml models, migrations, endpoint
├── bookshop_client/                 # generated by Serverpod
├── bookshop_flutter/                # the template app
└── bookshop_admin/
    ├── beak.yaml                    # serverpod + generate settings
    ├── definitions/                 # inventory + authored behavior
    ├── generated/                   # pure Dart, written by beak generate
    └── lib/                         # the Flutter panel
```

## At a glance

| You want | Look at |
| --- | --- |
| The reviewed admission | `bookshop_admin/definitions/resources/catalog.yaml` |
| The generated models | `bookshop_admin/generated` (run `beak generate`) |
| The server engine | `bookshop_server/lib/src/beak/bookshop_beak_engine.dart` |
| The panel | `bookshop_admin/lib/` |

## Run it

```console
$ cd examples/serverpod
$ flutter pub get
$ cd bookshop_admin && flutter run -d chrome
```

The server must be running (`serverpod start` in `bookshop_server`); sign in with
an account holding `beak.admin` and `bookshop.staff`.

## Tour

The inventory admits two models; the generator turns them into typed models;
the engine serves them; the panel declares two standard resources.

## Where things are

See the tree above. `generated/lib/` is gitignored: run `beak generate` after a
model, migration or inventory change.

## Features shown

- A generated list, detail page and form for each model.
- A relation picker and a relation filter.
- A server-only column omitted from the model and every response.
- Stock persistence admitted from the inventory.

## Tests

`flutter test` in `bookshop_admin` runs the real Beak pipeline over an in-memory
adapter. CI runs `beak generate --check`, analyze and the widget tests.

## Limits

Uploads, an outbox worker and row scopes are not mounted here; see
[Limits and next steps](../serverpod/admin-app/limits-and-next-steps.md).

## The inventory

```yaml title="examples/serverpod/bookshop_admin/definitions/resources/catalog.yaml"
area: catalog
resources:
  Book:
    display: title
    operations: [read, create, update]
    write: configuration
    writeFields: [title, isbn, format, priceInCents, stock, publishedOn, authorId]
  Author:
    display: name
    operations: [read, create, update]
    write: configuration
    writeFields: [name, bio, website]
```

Nobody deletes: a rule that is not written is closed, so removing a book or an
author is a deliberate server change.

## The engine

```dart title="examples/serverpod/bookshop_server/lib/src/beak/bookshop_beak_engine.dart"
--8<-- "examples/serverpod/bookshop_server/lib/src/beak/bookshop_beak_engine.dart:bookshopBeak"
```

`bookshopModels`, `bookshopDefinitions` and `BookshopWrite` come from the
generated package and the definitions package. The endpoint keeps its sign-in
and scope gate.

## The panel

`runServerpodBeakAdmin` builds the client, restores the session, resolves the
token scopes and tunnels every request through `client.beakAdmin.dispatch`.
`BookResource` and `AuthorResource` are `BeakResource` declarations over the
generated models.

## What it proves

- The schema package is generated from `.spy.yaml`, the newest migration and the
  inventory; `beak generate --check` runs in CI.
- Writes use stock persistence; a use case joins them with
  `BeakWriteHandler.commands`.
- A server-only column such as `Book.supplierCostInCents` never enters the model
  or a response.
- The widget tests run the real Beak pipeline over an in-memory adapter, with no
  Serverpod process.
