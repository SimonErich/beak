# Admin app in your workspace

This section covers one setup: a Serverpod 4 workspace gains an admin app, and
Beak's API runs inside the Serverpod server behind one gated endpoint, on
Serverpod's own database. You keep Serverpod's tables, migrations, sign-in and
use cases.

## What the workspace looks like

| Package | What it is | You edit it |
| --- | --- | --- |
| `<name>_server` | The Serverpod server: `.spy.yaml` models, migrations, the Beak endpoint and the use cases | Yes |
| `<name>_client` | Generated by Serverpod, with `client.beakAdmin.dispatch` | Never |
| `apps/<name>_admin` | Flutter web panel: `beak.yaml`, `definitions/`, `lib/` | Yes |
| `apps/<name>_admin/generated` | Pure Dart schema package written by `beak generate` | Never |
| `apps/<name>_admin/definitions` | Reviewed inventory and authored behavior/rules | Yes |

The generated package depends on `beak_core` only, so the server can import the
same definitions without pulling in Flutter. The panel never reads a Serverpod
table directly: every request goes through the tunnel.

## What it proves

- One endpoint method, `beakAdmin.dispatch`, carries the whole Beak API.
  Serverpod answers 401 or 403 before any Beak code runs.
- The generated models carry permissions, capabilities and write admission from
  the reviewed inventory; the server enforces them again on every request.
- A write reaches an existing use case or stock persistence, never a second
  implementation.
- A server-only column never leaves the database: not in the model, a response,
  an export or a stored receipt.
