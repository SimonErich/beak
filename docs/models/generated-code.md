# Generated code

After this page you can read anything `beak prepare` writes and know why it is
there. None of it is a black box: it is ordinary Dart, committed to your
repository, and you can open any of it.

## What runs when

```bash
beak prepare
```

reads three inputs — the schema classes under `lib/models/`, the screens under
`lib/screens/`, and `beak.yaml` — and writes two kinds of output.

## Beside each model

```text
lib/models/
  product.dart         you wrote this
  product.beak.dart    generated, committed
```

The part file holds four things, all derived from the one class:

**`ProductColumns`** — a `static const` per field. This is what you point at
everywhere else, instead of writing `'price'` and hoping the strings match:

```dart
BeakSelectFilter(column: ProductColumns.status, label: 'Status')
```

**`ProductRelations`** — a `static const` per relationship, *including the ones
the other side declared*. `@BelongsTo() late final Category? category;` on
`Product` generates `ProductRelations.category` here and
`CategoryRelations.products` in `category.beak.dart`, so both sides exist and
neither can drift.

**`ProductModel`** — the `BeakModel` the API, the panel and the migration all
read. It is what you name in a `BeakResource`, a `BeakTableBlock` or a test.

**`ProductRecord`** — an extension type over `BeakRecord` giving typed getters:

```dart
final product = ProductRecord(record);
final double price = product.price;   // not record['price']?.raw as double
```

## Under `lib/beak/`

```text
lib/beak/
  registry.g.dart   every model, and the registry over them
  panel.g.dart      the BeakPanelConfig: resources, sections, icons, screens
  app.g.dart        the root widget
  server.g.dart     the BeakServeHost: registry, migrations, seeders
```

Four files, one concern each. `panel.g.dart` is the one worth reading: it is
exactly what you would have written by hand, assembled from `beak.yaml` and
what discovery found.

```dart title="examples/store/lib/beak/panel.g.dart"
resources: [
  BeakResource(
    model: const CategoryModel(),
    icon: BeakIconToken(OiIcons.folderTree),
    section: 'Catalog',
  ),
  resource_products.beakResource(
    BeakResource(
      model: const ProductModel(),
      icon: BeakIconToken(OiIcons.package),
      section: 'Catalog',
    ),
  ),
  // ...
],
```

The second entry is what a `lib/resources/products.dart` override looks like
from the outside: Beak derives the resource, then hands it to your file, which
returns the copy it wants.

## The entrypoints

```text
lib/main.dart      git-ignored
bin/serve.dart     git-ignored
bin/migrate.dart   git-ignored
```

Three files, one line each, at the paths Flutter and Dart expect so
`flutter run`, an IDE run button and `dart compile exe` work with no flags.
They are ignored because nothing about them is a decision worth reviewing —
`beak eject main` changes that if your team would rather commit them.

## The migrations

`beak prepare` also writes the migration a resource needs and does not have,
into `lib/migrations/`. Those are **not** regenerated: they are written once
and then yours. See [Migrations](../backend/migrations.md).

## What to commit

Everything except the three entrypoints. The generated code is part of your
source: it makes a fresh checkout compile without running a tool first, it
makes a diff show what a schema change actually did, and it means CI does not
need `beak` installed to build your app.

!!! warning "Do not edit a generated file"
    Every file starting with `// GENERATED BY \`beak prepare\`` is overwritten
    on the next run. To change what one contains, change the input: the schema
    class, `beak.yaml`, or the matching override file. `beak doctor` tells you
    when a generated file no longer matches its inputs.
