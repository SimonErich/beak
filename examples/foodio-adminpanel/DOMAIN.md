# Gabel demo domain

The Foodio folder preserves the prototype’s **Gabel** brand. This is a persistent SQLite demo: payment and message providers store their results locally and make no outbound provider calls. `bin/serve.dart` drains the durable outbox once per second.

## Reproduce the fixture

Use the verified Flutter 3.44.0 / Dart 3.12 toolchain consistently, run `beak prepare`, then `dart run bin/migrate.dart migrate` and `dart run bin/migrate.dart db:seed`. Copy `.env.example` to `.env` before starting `dart run bin/serve.dart` (port 8081). The seed runs once and preserves subsequent edits. `migrate:fresh --seed` deliberately resets the demo; it reverses registered migrations, recreates tables and reruns seeders. Unknown applied migrations cause an error before known tables are dropped. SQLite rebuilds the registered schema in one transaction, deferring foreign-key checks only until commit. Cyclic and forward relationships therefore reset safely; a failed replacement migration or surviving external reference rolls back all drops. Ordinary transactions retain immediate foreign-key enforcement.

The reference clock stays at 28 September 2026, 09:42 Vienna summer time. This keeps calendar queries and cutoff demonstrations reproducible. `FoodioClock` accepts an injected UTC clock for boundary tests; the fixed two-hour offset is specific to the reference week, not a general time-zone service.

The seed contains **48,213 actual orders** and their line items. Its queries produce 412 orders today, 664 future deliveries, 96 future orders awaiting release, seven attention items across all dates, three drafts and 148 orders for Lena. Today’s non-cancelled revenue is **€9,826.40**. The six mutually exclusive operational counts are 83 confirmed, 131 in kitchen, 64 out for delivery, 128 delivered, five needing attention and one cancelled. Workflow states are retained on attention records; charts intersect each ordinary status with `needsAttention == false` and give attention its own measure. The reference advanced filter returns 214 actual records. The seeded ORD-24817 contact phone uses Lena’s complete customer number; the prototype’s shortened contact text is corrected so new and existing order snapshots agree.

## Money and reservation rules

- Prices and totals use integer **VAT-inclusive cents**. VAT rates use basis points (1000 = 10%). Food has 10% VAT; beverages have 20%.
- One voucher applies first, optionally only to food and capped at its maximum, followed by a separate manual adjustment. Stable largest-remainder allocation distributes discount cents. VAT rounds once per rate bucket and reconciles to line totals.
- An unchanged catalog selection keeps its price, label, tax and option snapshots. Placed vouchers retain their percentage, cap, restriction and code even if the catalog voucher changes. Issued invoices freeze recipient and money snapshots.
- Adding or replacing a catalog selection requires an active profile menu plan containing that dish on the delivery date. Placement rechecks all selections. Unchanged historical lines retain their snapshots even after a menu changes or becomes inactive.
- Drafts reserve nothing. Every placed order, including pending approval/payment, reserves **one order** in its date-specific delivery slot, irrespective of portions.
- Creating a company profile initializes its current-month ledger. If an order is placed in the same graph for another month, that delivery-month ledger is created as well. Customer, profile, ledger and order identities resolve in one transaction; insufficient budget rolls all of them back. Private profiles create no company ledger.
- A company-funded order reserves its gross amount from its profile’s monthly budget. Insufficient budget blocks placement; approval never bypasses that limit. Orders above the profile threshold (€40 for the reference profile) also need approval.
- Cancelling before preparation releases capacity and reserved budget. Capacity already consumed by kitchen preparation remains consumed. Delivery converts a reserved budget amount into spent cents exactly once.
- Paid amounts and payment methods are locked. Cancel and refund a paid order before changing its financial terms; delivery instructions and other permitted nonfinancial edits remain available.
- One-time delivery addresses require explicit `addressOverride` intent, a selected active location and a nonempty street in that location’s city/postal area. The order stores the shipment address; saved location/profile records stay unchanged. Location organization eligibility, route and transport method remain authoritative. Turning the override off restores the location’s address. This demo models postal delivery areas, not a geocoding/routing provider.
- Same-day placement and content changes close at 10:30. Preparation locks customer, profile and delivery date. Dispatch/delivery/cancellation lock content. An explicit redelivery action accepts a new date and a slot validated against that date.

`FoodioOrderPreparer` runs inside Beak’s graph transaction. Capacity, budget and order-number compare-and-set updates roll back with any validation failure. Parent totals are calculated from the full final child graph. Direct CRUD cannot bypass the configured transactional tables; action-controlled states and derived values are checked again on the server. Removing a saved child also enforces its revision precondition for hard and soft deletion, so a stale editor cannot delete a row changed elsewhere. Unchanged submitted rows retain their stored timestamps and snapshots while still receiving applied-operation receipts and a guarded SQL comparison. The note command accepts those unchanged populated form rows and rejects material changes to the order.

## Effects and actions

Named model actions declare availability and state transitions. Placement, approval, rejection, kitchen start, dispatch, delivery, cancellation, payment retry/link, allergy acknowledgement and redelivery use the same declarations in forms and API requests. Invoice issue/payment/cancellation are also named actions. `addNote` collects a required, bounded internal note through a transient input model and appends it atomically with server-authored actor/time, including on finished orders. `amend` accepts an optional note and applies it in the same transaction as allowed order edits; empty notes leave normal Save changes usable. Failed domain validation rolls back both the edit and note, and receipt replay appends the note once. The separate `addNote` command still rejects material order changes. Saved notes cannot be rewritten or deleted. Operational approval, payment, allergy and change-resolution commands exclude drafts and terminal orders; note creation remains independently available.

The transactional finalizer enqueues confirmation, approval, payment, refund or payment-link effects with a stable save-derived key. The worker delivers at least once. `PaymentAttempt` and `MessageDelivery` persist a provider receipt under that key, so retrying after a process dies between delivery and acknowledgement does not charge, refund or send again. Each effect records audit activity. Effect updates advance the same monotonic millisecond revision as normal saves, even with the fixed demo clock, so an open stale editor cannot overwrite a payment result. Obsolete charges are skipped if the order was cancelled, collection completed, or its amount, payment mode or method changed. Messages for cancelled orders, resolved approvals and obsolete payment links also persist skipped receipts. Payment methods with `demoOutcome: declined` exercise the failure/retry path. Demo payment-link URLs identify the simulated provider and do not represent a real payment service.

## Declarative configuration

`BeakValueBehavior.suggested` supplies the selected customer’s active default profile, location/payment defaults and variant/option labels and prices. New orders initially deliver tomorrow according to the demo clock; delivery slots remain an explicit selection. Explicit user overrides survive recomputation. Suggested values do not initiate inverse writes into older referencing snapshots; true derived values still propagate. Selecting only an order item’s variant resolves its owning dish automatically. New dish and option selections suggest their allergen snapshots, and dish selections suggest their food classification as well as price and VAT. Food-only voucher previews therefore exclude drinks before saving and agree with the server; unchanged saved selections retain their original classification and allergens.

`DeliveryProfileModel.budgets` exposes monthly ledgers through ordinary typed eager loads, including `OrderModel.profile.budgets`, for a budget preview without an application fetch controller. The model suggests an active saved method of the selected payment kind, preferring its default and retaining an eligible current selection; non-saved payment modes clear the suggestion. Explicit manually overridden selections remain subject to the normal eligibility checks. The model scopes payment-method selections to active identities of the chosen customer; placement also requires PayPal identities for PayPal and card identities for card/subsidy-card modes. Newly staged customers and saved methods satisfy the same rule atomically. A payment link supports customers without a saved method. Notes receive a shared initial timestamp and a server-authored actor/time.

The wizard's budget bar and caption compare this order's company-funded amount with the budget available before this order. An empty or personally funded order contributes zero. When editing an existing reservation in the same profile and month, its previous amount becomes available exactly once before charging the edited amount. The separate budget-after metric still subtracts all projected reserved and spent money from the monthly allowance.

Rich catalog and search pickers clear obsolete results as soon as a new term starts debouncing. Global date formatting initializes bundled locale symbols automatically; applications do not need an intl startup hook.

Supporting resources use shared cards and tabs for customers, organizations, profiles, staff, locations, invoices, vouchers, budgets, slots, menus, complaints and settings. Currency inputs convert displayed euros to integer cents. Reservation counters and invoice totals are read-only; internal sequence settings are excluded and protected on the API. Customer names and joining dates and menu-item names come from model behaviors rather than application controllers.

`@EnumLabels<OrderStatus>({OrderStatus.inKitchen: 'In kitchen'})` and `@Badges<OrderStatus>({...})` supply labels and semantic colors to every generated view/input/filter while the stored enum remains `inKitchen`. Handwritten columns may use `BeakEnumColumn.labels`; an explicit `labelOf` callback takes precedence.

`BeakSummaryMeasure.count('attention', filter: OrderModel.needsAttention.eq(true))` defines a conditional measure. Count and sum filters intersect the shared summary population, search, soft-delete scope and policy. Field and relationship authorization applies to every measure predicate. Empty grouped measures are zero-filled; result overflow remains explicit.
