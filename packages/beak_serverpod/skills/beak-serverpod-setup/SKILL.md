# Beak admin on Serverpod

Beak's stock API runs inside the Serverpod server behind one gated endpoint
method, on Serverpod's own database, sessions and transactions. There is no
second server and no second database. Serverpod stays the owner of tables,
migrations, sign-in and scopes; Beak adds the panel, and its policy decides who
may do what inside the tunnel.

| Package | What it is | You edit |
| --- | --- | --- |
| `<name>_server` | `.spy.yaml` models, `lib/src/beak/` (endpoint, engine, policy, scopes), `bin/beak_admin.dart` | yes |
| `<name>_client` | generated by Serverpod | never |
| `<name>_beak` | pure Dart schema classes mirroring the tables, plus generated parts | the schema classes and the barrel |
| `<name>_admin` | Flutter web: resources and `lib/main.dart` | yes |

Never edit `lib/src/generated/`, `<name>_client`, `*.beak.dart` or `*.g.dart`.
Read first: the workspace `AGENTS.md` (Serverpod's own rules apply), any
installed `serverpod-*` skills, and by path
`.dart_tool/beak/docs/serverpod/admin-app/setup.md`,
`.dart_tool/beak/docs/serverpod/admin-app/how-it-works.md`,
`.dart_tool/beak/docs/serverpod/authentication.md` and
`.dart_tool/beak/docs/serverpod/versions.md`. Folder missing? Run `beak docs`
after the first `dart pub get`.

## Never

Never start the server yourself, and never run `dart run bin/main.dart`. Ask the
user to run `serverpod start` (Ctrl+R launches the apps listed under
`serverpod: flutter_apps:`), or use the Serverpod MCP tools when they are
connected. The same goes for anything that needs the database: applying a
migration, `bin/beak_admin.dart grant`.

## Set up

1. Read the exact `serverpod` version from the server pubspec. Every `serverpod*`
   package stays on that exact pin; Beak's own packages all use one release tag,
   the one `beak --version` prints (`ref: v0.9.0`). Serverpod 4.0.3 needs Dart
   3.12.2 and Flutter 3.44.4 or newer.
2. Create `<name>_beak` and add it to the workspace. Mirror each table the admin
   shows as a schema class (`@Resource(table: ..., managesSchema: false)`); leave
   out every column the admin must not see. Run `beak prepare` inside it. Files
   and the type mapping: `references/beak-package.md`.
3. In the server add the dependencies, Beak's receipt model
   (`lib/src/beak/models/beak_commit_receipt.spy.yaml`, copied verbatim), the
   scopes, the `BeakPolicies` rule set, the `BeakServerpodEngine` and the
   `BeakAdminEndpoint` with the `BeakAdminGate` mixin, and `bin/beak_admin.dart`:
   `references/server-files.md`. The policy names every model and every
   operation it allows; whatever it does not name is closed.
4. Run `serverpod generate` in the server directory (it creates
   `client.beakAdmin.dispatch`), then `serverpod create-migration` (it writes
   the migration for the receipt table and any changed tables). Applying it
   needs the database: ask the user to run `serverpod start`, or use the MCP
   tool.
5. Create `<name>_admin`, add it to the workspace, and write `lib/main.dart`, the
   panel and one resource per model: `references/admin-files.md`. Optionally list
   it under `serverpod: flutter_apps:` in the server pubspec so `serverpod start`
   can launch it.
6. Ask the user to grant access and sign in again:
   `dart run bin/beak_admin.dart grant <email>` (run in the server package; the
   account must exist, so sign up in the admin first). Scopes are copied into a
   token when it is issued.
7. Add the tests (server gate and policy, mirror test, admin widget tests) and
   run the gate.

## Every later change

1. Edit the `.spy.yaml` (or the endpoint). Hand-edit a generated `migration.sql`
   only when its SQL would lose data.
2. `serverpod generate`, then `serverpod create-migration` in the server
   directory. If the server is not running, ask the user to start it.
3. Update the matching schema class in `<name>_beak` (`references/beak-package.md`
   has the mapping), then `beak prepare` there.
4. Name any new table in the policy file (`lib/src/beak/<name>_policy.dart`); a
   new table is closed until it is.
5. Update resources and screens (`beak-frontend-build-screens`), then test.
6. A column the admin must not see stays out of the schema class. Never model it
   and hide it in a widget.

## Gate

- Server package: `dart analyze`, `dart test` (the tests use Serverpod's own test
  database setup; the mirror test fails when a Beak column is not a physical
  column or an enum drifted).
- `<name>_beak`: `dart analyze`, `beak prepare` leaves no diff.
- `<name>_admin`: `dart format .`, `flutter analyze`, `flutter test`.
- Every endpoint test proves a signed-in user without `beak.admin` is refused.

## Example prompt

```text
Use the beak-serverpod-setup skill to add a Beak admin to this Serverpod workspace for the Author and Book tables: staff read and write, nobody deletes, supplierCostInCents never leaves the server. Don't start the server; tell me when to run serverpod start.
```
