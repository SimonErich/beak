# Serverpod admin app

> The reference Serverpod workspace, whose Beak admin is generated from one definition class per exposed model, with every write through the engine.

`examples/serverpod` is the reference workspace: three packages from
`serverpod create` (`bookshop_server`, `bookshop_client`, `bookshop_flutter`)
and two Beak packages under `bookshop_admin` (the panel and `definitions`).

```text
examples/serverpod/
├── bookshop_server/                 # .spy.yaml models, migrations, endpoint
│   └── lib/src/beak/generated/      # BookshopHandlers, written by beak generate
├── bookshop_client/                 # generated by Serverpod
├── bookshop_flutter/                # the template app
└── bookshop_admin/
    ├── beak.yaml                    # serverpod + generate settings
    ├── definitions/                 # Book and Author definition classes
    ├── labels/                      # model and field names
    └── lib/                         # the Flutter panel
```

## At a glance

| You want | Look at |
| --- | --- |
| The definition classes | `bookshop_admin/definitions/lib/src/catalog/` |
| The generated models | the `*.beak.dart` parts and `definitions/lib/src/generated/` (run `beak generate`) |
| The server engine | `bookshop_server/lib/src/beak/bookshop_beak_engine.dart` |
| The panel | `bookshop_admin/lib/` |

## Run it

```console
$ cd examples/serverpod
$ flutter pub get
$ cd bookshop_admin && flutter run -d chrome
```

The server must be running (`serverpod start` in `bookshop_server`); sign in with
an account holding `beak.admin` and `bookshop.staff`.

## Tour

Two definition classes expose `Book` and `Author`; the generator checks them
against Serverpod and writes their parts and the handler aggregate; the engine
serves them; the panel declares two standard resources.

## Where things are

See the tree above. Run `beak generate` in `bookshop_admin` after a model,
migration or definition class change.

## Features shown

- A generated list, detail page and form for each model.
- A relation picker and a relation filter.
- A server-only column left out of the class, so it is not in the model or any
  response.
- Stock create and update opened on the definition class.

## Tests

`flutter test` in `bookshop_admin` runs the real Beak pipeline over an in-memory
adapter. CI runs `beak generate --check`, analyze and the widget tests.

## Limits

Uploads, an outbox worker, custom handlers and row scopes are not used here; see
[Limits and next steps](../serverpod/admin-app/limits-and-next-steps.md).

## The definition classes

```dart title="examples/serverpod/bookshop_admin/definitions/lib/src/catalog/book.dart"
@Resource()
@ServerpodAdminModel(
  area: 'catalog',
  create: BeakHandling.stock,
  update: BeakHandling.stock,
  commands: [BeakCommand('restock')],
)
final class Book extends BeakSchema {
  /// The commands staff can run on a book.
  static BeakModelBehavior get behavior =>
      BeakModelBehavior(actions: [BookActions.restock]);

  /// The title printed on the cover.
  @Display()
  late final String title;

  /// The ISBN, unique per edition.
  late final String isbn;

  /// How the book is bound.
  late final BookFormat format;

  /// Shelf price in cents.
  late final int priceInCents;

  /// Copies on the shelf.
  late final int stock;

  /// First publication date.
  late final DateTime? publishedOn;

  /// Who wrote it.
  @BelongsTo()
  late final Author? author;
// ...
}
```

Nobody deletes: `delete` stays `off`, so removing a book or an author is a
deliberate server change.

## The engine

```dart title="examples/serverpod/bookshop_server/lib/src/beak/bookshop_beak_engine.dart"
/// The bookshop's Beak engine: one per process, shared by every request.
///
/// It serves Beak's stock API for the bookshop's definition classes on the
/// request's own Serverpod session, so every statement runs on Serverpod's
/// database with its transactions and logging. Book runs its restock command
/// through the app's typed handler; Author is saved the stock way.
final BeakServerpodEngine bookshopBeak = BeakServerpodEngine.admitted(
  models: bookshopModels,
  handlers: const BookshopHandlers(book: BookAdminHandler()),
  principal: BeakServerpodPrincipal.fromScopes,
);
```

`bookshopModels` comes from the definitions package and `BookshopHandlers` from
the generated handler folder. The endpoint keeps its sign-in and scope gate.

## The panel

`runServerpodBeakAdmin` builds the client, restores the session, resolves the
token scopes and tunnels every request through `client.beakAdmin.dispatch`.
`BookResource` and `AuthorResource` are `BeakResource` declarations over the
generated models.

## What it proves

- The models are generated from `.spy.yaml`, the newest migration and the
  definition classes; `beak generate --check` runs in CI.
- Writes use stock persistence; a model that needs a use case opens the
  operation as `custom` and implements the generated handler.
- A server-only column such as `Book.supplierCostInCents` never enters the model
  or a response.
- The widget tests run the real Beak pipeline over an in-memory adapter, with no
  Serverpod process.
